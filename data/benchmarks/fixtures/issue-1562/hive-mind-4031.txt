Auto-restart on uncommitted changes never applies its "No progress" stop when an old session-kill notice is counted as a new comment

## What happens

Run: `solve <issue-url> --model formal-ai --tool codex --attach-logs --verbose --no-tool-check --disable-report-issue --language en`, solve v2.39.10, 2026-11-10, pull request https://github.com/konard/test-hello-world-019fb331-c107-78c7-8ff6-9f127a3c593c/pull/2. The provider is only the one used in the evidence run; nothing below depends on the model or the tool.

Log (2837 lines): https://gist.githubusercontent.com/konard/f0e689ac80237a960f865873b14f38b8/raw/1eae4c63babdd5783808d7c0f71330c3919dea2c/tmp-hive-mind-log-upload-usQxob-sanitized.log.txt (quotes below omit the timestamp prefix and the leading emoji).

## Expected

A restart loop stops as soon as a session repeats the previous one, whatever started the loop. A comment that Hive Mind itself posted three weeks earlier does not count as new human feedback, and one comment cannot switch the guard off for every iteration of a run.

## Root cause

Code read at 2.39.14 (commit b245deb62fbbca42625753587575416c50d81727). The evidence run is 2.39.10; whether the cited lines are identical in 2.39.10 was not verified.

Three things combine.

1. The repeat guard is skipped whenever any new comment is counted. [`src/solve.watch.lib.mjs` lines 341-343](https://github.com/link-assistant/hive-mind/blob/b245deb62fbbca42625753587575416c50d81727/src/solve.watch.lib.mjs#L341-L343):

   ```js
   const hasNewHumanComments = newPrComments + newPrReviewComments + newIssueComments > 0;
   noProgressStop = hasNewHumanComments ? null : await stopWhenSessionRepeated({ ... mode: 'watch' ... });
   if (noProgressStop) break;
   ```

   `src/solve.restart-shared.lib.mjs` lines 546-549 only print the "No progress" line; they stop nothing.

2. Every feedback check in the run reports one new comment (lines 161-164, 731-734, 1157-1160, 1585-1588, 2013-2016, 2441-2444):

   ```
   Last commit time:       2026-10-20T22:35:56.000Z
   New PR comments:        1
   New PR review comments: 0
   New issue comments:     0
   ```

   The only comment that is newer than that commit and is not filtered is https://github.com/konard/test-hello-world-019fb331-c107-78c7-8ff6-9f127a3c593c/pull/2#issuecomment-6303319315, created 2026-10-20T22:36:24Z. It is Hive Mind's own session-kill notice; its first line is `<!-- hive-mind:session-kill-notice -->`. That marker (`KILL_RECOVERY_NOTICE_MARKER`, `src/session-kill-recovery.lib.mjs` line 33) is not in `TOOL_GENERATED_COMMENT_MARKERS` ([`src/tool-comments.lib.mjs` lines 152-154](https://github.com/link-assistant/hive-mind/blob/b245deb62fbbca42625753587575416c50d81727/src/tool-comments.lib.mjs#L152-L154)), so `isToolGeneratedComment` (lines 176-179) returns false, and no `logPatterns` entry in `src/solve.feedback.lib.mjs` (line 104) matches it either. `isToolStatusComment` (lines 194-199) would accept the `<!-- hive-mind:` prefix, but the feedback counter does not use it.

   Checked by matching the comment body text against the 34 markers and the log patterns of the source (0 hits). The neighbouring comment 6303318912 ("Intermediate working-session log (killed session)") has hits and is filtered. The source was not executed.

3. The counting window is "since the last commit" (`src/solve.feedback.lib.mjs` line 74). A loop whose problem is that nothing gets committed never moves that window, so the same comment is counted again on every iteration.

Result: `hasNewHumanComments` is true for all five restarts and `stopWhenSessionRepeated` is never called.

## Suggested fix

- Treat every comment that starts with a `<!-- hive-mind:` marker as tool-generated in `isToolGeneratedComment`, or at least add `KILL_RECOVERY_NOTICE_MARKER` to `TOOL_GENERATED_COMMENT_MARKERS`.
- Add a test that every marker constant the solver writes into a comment is recognised by `isToolGeneratedComment`, so a new comment type cannot be forgotten again.
- Inside a restart loop, count a comment as new only once: remember the comment ids already seen in this run (or use the start of the previous session as the window when no commit was made). The repeat guard is then skipped at most for the one iteration that follows real feedback.
- Keep the guard itself identical in both loops (see #1355).
