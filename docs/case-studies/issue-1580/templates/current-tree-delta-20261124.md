Formal AI's crate waiter could previously report that a release was absent when one registry endpoint returned invalid data with HTTP 200 and the other returned HTTP 404. It also accepted a matching version with the wrong API crate name, and an index row with invalid SemVer could pass beside an exact match. The repair decodes the full response as UTF-8, validates every sparse row and checks the API crate name when present. A valid exact match can settle availability after a failed observation. A malformed success leaves availability uncertain when the peer supplies only evidence of absence.

To reproduce, the native CLI test runs the waiter with two bounded attempts against a loopback registry. It builds the archived pre-fix registry module from commit `02b4076e7` and the revised source against the same inputs. The six failure cases cover invalid JSON and UTF-8 on both endpoints, a malformed indexed version after an exact match, and a matching API version for the wrong crate. The revised waiter is expected to produce an uncertainty diagnostic and leave `GITHUB_OUTPUT` absent. The positive controls exercise case-insensitive crate identity, a valid prerelease version with build metadata, and ordinary absence when the peer returns a transient HTTP error. GitHub Actions runs these binaries through the existing release-registry job. [Native CLI controls](../../../../experiments/issue-1580/release-registry/sparse_registry_regressions.py)
