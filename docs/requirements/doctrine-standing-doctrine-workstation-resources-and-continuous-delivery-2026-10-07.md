## Standing Doctrine: Workstation Resources and Continuous Delivery (2026-10-07)

Recovered from the owner's directives while continuing PR #1188
(`experiments/issue_1138_feedback_recovery/recovered-2026-10-07.md`) and
diffed against the register: these were stated but not yet recorded. They
govern how work is done on the owner's workstation and when a pull request
counts as finished, alongside the work-in-bulk rule of CONTRIBUTING.md and the
delegation doctrine of
[R1017](doctrine-standing-doctrine-work-delegated-to-formal-ai-2026-10-07.md).

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1018 | Local verification runs a single test (one test file) at a time, never a parallel suite: `node --test --test-concurrency=1 <file>` and the serialized `npm run test:web`. When the workstation's CPU is overloaded by test processes, the owner's processes are never killed; the root cause (unbounded test concurrency, a runaway runner) is fixed instead. (Owner, 2026-10-06 21:18/21:19.) | Implemented: `npm run test:web` runs `node --test --test-concurrency=1` (package.json), and CONTRIBUTING "Work in bulk; verify selectively" now states the single-test rule and the never-kill rule; every sub-agent brief of PR #1188 carried the `while pgrep -f "^node --test"` serialization guard. Pinned by `rust/tests/unit/docs_requirements/doctrine_2026_10_07.rs` (`local_verification_runs_one_test_file_at_a_time`). |
| R1019 | No more than two or three sub-agents run at once, chosen with the workstation's disk, RAM and CPU in mind; every sub-agent is told the same limits. Sub-agents only make code changes; they run the JavaScript Formal AI only when absolutely necessary and never run builds or full suites, because CI/CD checks everything. (Owner, 2026-10-06 20:17/20:32.) | Implemented as a process rule: CONTRIBUTING "Delegate to Opus sub-agents only" now names the two-to-three cap, the shared resource limits and the code-changes-only scope; PR #1188's case study (`docs/case-studies/pull-request-1188/`) records the cap being kept. Pinned by `rust/tests/unit/docs_requirements/doctrine_2026_10_07.rs` (`sub_agents_are_capped_and_make_code_changes_only`). |
| R1020 | Rust is never built locally to check a change: a Rust build or test is triggered by pushing, and CI/CD is the Rust verifier. Artifacts that need a Rust build (the WASM worker, `ts/` translation) are produced by CI or by a JavaScript twin. (Owner, 2026-10-06 13:17: "minimize rust building or delegate it fully to CI/CD (meaning to trigger Rust builds we just do push)".) | Implemented as a process rule: CONTRIBUTING "Work in bulk" states that Rust is verified by pushing; the WASM worker is refreshed from the CI-built `formal-ai-worker-wasm` artifact the release workflow uploads (`.github/workflows/release.yml`), and `ts/` is produced by the JavaScript twin `scripts/translate-es.mjs`. Pinned by `rust/tests/unit/docs_requirements/doctrine_2026_10_07.rs` (`rust_is_verified_by_pushing_and_its_artifacts_come_from_ci`). |
| R1021 | The requirement status recorded in the repository is kept current while a pull request is worked on: each batch that changes what is delivered updates the owning requirement rows and regenerates the assembled register in the same push, rather than at the end. (Owner, 2026-10-06 20:08: "continue to recheck and update status of requirements in the repository".) | Implemented: each batch of PR #1188 regenerates the assembled register and the requirement-status ledger (`scripts/assemble-requirements.rs`, `scripts/generate-requirement-status.rs`, `scripts/render-status.rs`) in the same push, and `rust-script scripts/check-requirement-status.rs` gates the parity. Pinned by `rust/tests/unit/docs_requirements/doctrine_2026_10_07.rs` (`requirement_status_is_regenerated_with_each_batch_and_gated`). |
| R1022 | Work on a pull request does not idle-wait: while CI runs, the agent re-reads the requirements, the pull request and the code and re-verifies each planned requirement; it stops only when every planned requirement is delivered, CI/CD is green, and the release is guaranteed deliverable. (Owner, 2026-10-06 17:00, 18:36, 18:52; 2026-10-07 05:32, 05:36: "Why waiting again? Did you check that everything is fully done?") | Implemented as a process rule in CONTRIBUTING "Work in bulk": while CI runs, the agent keeps drafting the open requirement rows; the PR #1188 case study records the rows drafted during CI waits.
