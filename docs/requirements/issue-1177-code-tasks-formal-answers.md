## Issue #1177 Code Tasks Answered Formally

Issue [#1177](https://github.com/link-assistant/formal-ai/issues/1177) (E142,
part of the #1183 umbrella) gives the solver nine code-task families —
debugging, regular-expression synthesis, SQL synthesis, shell-command
composition, code explanation, code review, test generation, code
refactoring, and JSON/YAML format conversion — as structural derivations
from seed vocabulary, with every answer stating honestly that no code,
query, command, regex or generated test was executed. The probes, the
before/after evidence, and the honest boundaries live in
`docs/case-studies/issue-1177/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1177-1 | A "find the bug / debug this" request over a function is answered by deriving the defect structurally — a binary `+`/`-` applied at top level after a division shifts the quotient and contradicts what the function name promises — with the line quoted, both fixes shown (reorder, parenthesize), and the property grounded in a source. | Partial: `handle_code_debugging` in `rust/src/solver_handlers/code_debugging.rs` reads `def`/`fn`/`function` lines, resolves the name's promised property against the `function_intent` records in `data/seed/meanings-code-structure-explanations.lino` (each with a math source URL), and flags `sum(xs) / len(xs) - 1` as mean-minus-one with both candidate fixes; inline one-line returns are scanned too. A second defect class needs no function name: a loop bound from the seeded `index_bound_past_end` table in `data/seed/code-task-cues.lino` (`range(len(xs) + 1)`, `<= len(xs)`, `<= arr.length`, `<= v.size()`, `<= v.len()`) is reported only when the same code indexes that collection, with the bound that stops one position earlier (`handler_code_debugging_reports_a_loop_bound_past_the_end`; JS twin in `js/worker/formal_ai_worker_code_tasks.js`, pinned by `rust/tests/web/issue-1177-code-tasks-parity.test.mjs`). A third class is an assignment inside a parenthesized condition that opens with a head from the seeded `assignment_in_condition` table (`if (`, `while (`). It needs a lone `=` at the condition's top level, outside quoted text, so a deliberate nested `while ((line = read()) != null)` is not reported. The fix is the comparison (`handler_code_debugging_reports_an_assignment_inside_a_condition` and its browser twin). Other defect classes fall to the honest no-defect template, which names all three covered classes. No code is executed and the answer says so. |
| R1177-2 | A regular-expression request ("five digits optionally followed by a hyphen and four digits") is composed from count, class, separator, optionality and anchor vocabulary, verified structurally, and never run against a string. | Partial: `handle_regex_synthesis` in `rust/src/solver_handlers/regex_synthesis.rs` composes from the seed word maps in `data/seed/code-task-cues.lino` (number words, classes, separators, optional markers, anchor exceptions) into anchored patterns — `^\d{5}(-\d{4})?$`, `\d{3,}` for "three or more" — and `verify_structurally` rejects dangling escapes and unbalanced repetition/parens/classes before answering. Unresolvable requests are refused by name. No match is executed and the answer says so. |
| R1177-3 | A SQL request ("select all users older than 30") is composed into a SELECT with table, columns, WHERE filters, aggregate, ORDER BY and LIMIT — each clause mapped back to the request words that produced it — and nothing is executed against a database. | Partial: `handle_sql_synthesis` in `rust/src/solver_handlers/sql_synthesis.rs` composes the statement from seed comparatives ("older than N" → `age > N`), generic column comparisons, named filters, aggregates, "sorted by X" and "top N" cues; the answer carries a request→emission mapping row per clause and states the verification is by construction. An aggregate is grouped by the column a seeded grouping cue names (`sql_grouping` in `data/seed/code-task-cues.lino`: "per country", "for each department", "grouped by city", "для каждого …") — `SELECT country, COUNT(*) FROM users GROUP BY country;` with its own mapping row — and the browser twin composes the same statement (`handler_sql_synthesis_groups_an_aggregate_by_the_seeded_cue`, `rust/tests/web/issue-1177-code-synthesis-parity.test.mjs`). A threshold stated after the grouping becomes HAVING on the aggregate: a seeded `sql_having` cue ("having", "with", "имеющих") followed by a seeded `sql_threshold` comparator ("more than", "at least", "меньше", …) gives `SELECT customer, COUNT(*) FROM orders GROUP BY customer HAVING COUNT(*) >= 3;`. That span is no longer read as a WHERE filter, which before this fix emitted `WHERE with > 5`. A comparison stated before the grouping stays in WHERE (`handler_sql_synthesis_filters_groups_with_having_after_the_grouping` and its browser twin). Still single SELECT statements: no joins or subqueries. Identifying neither table nor cue refuses by name. |
| R1177-4 | A file-finding request ("find .log files larger than 10 MB under /var") is composed into a shell command with a cited manual page, and not executed. | Partial: `handle_shell_command_compose` in `rust/src/solver_handlers/shell_command_compose.rs` composes `find` with `-name` and `-size` clauses from the seed `file_context` and `size_unit` maps (MB/MiB → `M`, KB/KiB → `k`), cites the findutils manual, and marks the command Not executed. Beyond `find`, the same composer (twin `js/worker/formal_ai_worker_shell_compose.js`) reads four more verb families from seed cues, each flag explained from its manual page: line slices (`head`/`tail -n`, "show the last 20 lines of app.log"), content search (`grep -r`, with `-i` for an ignore-case cue and a Russian containment cue), directory listings (`ls`), and a seeded counting cue that pipes the result into `wc -l`. Pinned by `handler_shell_compose_slices_lines_and_searches_content` and the counting and Russian-grep tests in `rust/tests/unit/issue_1177_code_task_handlers.rs`, and by `rust/tests/web/issue-1177-shell-compose-parity.test.mjs`. A substitution request ("replace 1.0 with 2.0 in version.txt", "замени foo на bar в файле config.txt") composes `sed -i 's/1\.0/2.0/g' version.txt`. It reads seeded `substitute` / `substitute_with` role words, escapes the pattern and the replacement so they match literally, and refuses a word that holds the delimiter or a quote. Both flags are explained from the GNU sed manual record (`handler_shell_compose_composes_a_literal_sed_substitution` and its browser twin). A substitution with no file argument is not claimed. Verbs outside these families (awk, xargs pipelines, archive tools, sed scripts beyond one literal substitution) are refused by name rather than guessed. |
| R1177-5 | An "explain this code" request is answered line by line: each line matched against a construct table with a grounding URL, placeholders filled from the actual code, and an overall summary of what the function name promises. | Partial: `handle_code_explanation` in `rust/src/solver_handlers/code_explanation.rs` matches constructs (def, return, division, loops, builtins, conditionals, promise chains) from `data/seed/meanings-code-structure-explanations.lino`, each with sentence template and source, and closes with the name-promise summary. Unknown lines are skipped, not guessed; no code is executed and the answer says so. |
| R1177-6 | A "review this code" request reports only rule findings the code actually matches, each with severity, the quoted line, advice, and an upstream source URL — and no lint tool is run. | Partial: `handle_code_review` in `rust/src/solver_handlers/code_review.rs` applies the five seed rules in `data/seed/code-review-rules.lino` — bare `except:`, mutable default argument, `== None` instead of `is None`, `+=` string building in a loop (Python), loose `==` coercion (JavaScript) — each citing docs.python.org, PEP 8 or MDN. Language is detected from markers; a clean review says no match was found. No linter is executed and the answer says so. |
| R1177-7 | A "write tests for `f(x)`" request emits a runnable-looking pytest suite for a recognized problem shape, with expected values the shape's table states — and the suite is never executed. | Partial: `handle_test_generation` in `rust/src/solver_handlers/test_generation.rs` matches the function under test to the seed `test_cases` shapes (palindrome, average, max; trigger words are seed data), emits parametrized cases from the stated expectations (`RaceCar` → true, `never odd or even` → true, `[2, 4, 6]` → 4), and adds a `normalize()` helper when case-insensitivity/space/punctuation cues are present. Unknown shapes get a smoke skeleton and the derivation says the shape was not recognized. NOT executed, and the answer says so. |
| R1177-8 | A refactoring request performs the one implemented structural transformation — a JavaScript promise chain becomes an `async function` with `await`, handler bodies preserved verbatim — and refuses anything else by name. | Partial: `handle_code_refactoring` in `rust/src/solver_handlers/code_refactoring.rs` parses `.then`/`.catch` chains (arrow and `function` handlers), renders each `.then` as `const <param> = await <previous>;` in order with the catch clause preserved, and states the equivalence check is structural. Promise chains are the one transformation; other refactoring targets are refused by name. No code is executed and the answer says so. |
| R1177-9 | A JSON↔YAML conversion request converts the document, round-trips the result through the same subset parser, and compares against the input value; anything outside the subset is refused with a named reason. | Partial: `handle_format_conversion` in `rust/src/solver_handlers/format_conversion.rs` renders a JSON `Value` to block-style YAML and parses YAML back with a subset parser (mappings, sequences, scalars); the round-trip value equality check gates the answer, and bad JSON, a failed round trip or non-subset YAML each refuse through their own seed reason template. The subset excludes anchors, multi-line literals and flow style. No file or network I/O. |
| R1177-10 | All nine families are pure functions of seed data — cues, word maps, rule tables and answer prose live in `data/seed/` — refuse unrelated prompts, and are covered by automated tests at handler and engine level. | Implemented: recognition cues and word maps are in `data/seed/code-task-cues.lino`, review rules in `data/seed/code-review-rules.lino`, response templates in `data/seed/multilingual-responses.lino`, and every new intent key, scope, role and package token is defined in `data/seed/meanings-code-task-templates.lino`. `rust/tests/unit/issue_1177_code_task_handlers.rs` pins all nine probes at handler and engine level (the dispatch rows are wired in `rust/src/solver_dispatch.rs`), plus the refusal of unrelated prompts. All nine have browser-worker twins (`rust/tests/web/issue-1177-code-tasks-parity.test.mjs`, `issue-1177-code-synthesis-parity.test.mjs`, `issue-1177-format-conversion-parity.test.mjs`, `issue-1177-shell-compose-parity.test.mjs`), and `ts/` is regenerated from them. |
