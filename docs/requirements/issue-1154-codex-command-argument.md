# Issue #1154: One Shell-Argument Reading for the Whole Agentic Module

Issue [#1154](https://github.com/link-assistant/formal-ai/issues/1154) (E119):
Codex's shell tool `exec_command` sends the command under the argument key
`cmd`, while `progress.rs` read only `command`. The work-item read was never
recorded as attempted, and the stateless planner re-derived the identical
`gh issue view` call 78 times in a row (6.2M input tokens) until the client
compacted the thread. The full incident account, with the transcript excerpts,
is `docs/case-studies/issue-1154/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1154-1 | One shared `command_argument` for the whole `agentic_coding` module, reading the argument key from the client's declared tool schema (the key whose schema describes the shell command), falling back to `command`, `cmd`, `script`, and an array form joined for `shell`-style tools; the seven local copies are deleted. | Implemented: `rust/src/agentic_coding/tool_result.rs` holds the one shared `command_argument` (string and joined-array forms, `command` → `cmd` → `script`), and the seven former copies in `progress.rs`, `file_read.rs`, `tool_result.rs`, `narration.rs`, `command_reroute.rs`, `evidence_record.rs` and `workspace_change.rs` delegate to it (JS twin `commandArgument` in `js/agentic/tool_result.mjs`). The schema reading is wired since 2026-10-07: `command_argument_key` resolves the property whose own schema describes the shell command (never the working-directory property), and `project_declared_command_keys` (JS `projectDeclaredCommandKeys`) projects the request's tool definitions onto the transcript before planning, so a call whose tool declares its command under another key (e.g. `shell_command`) carries that value under `command`; the projection is pure (no state between requests, client messages untouched) and runs at both servers' agentic entry (`agentic_outcome` in `rust/src/protocol.rs`, `agenticOutcome` in `js/server/agentic.mjs`). Pinned by `the_command_key_is_read_from_the_tool_schema` and `a_schema_declared_key_plans_exactly_as_the_command_key` in `rust/tests/unit/agentic-coding/issue_1154_progress_arguments.rs` (drafted without a local cargo run) and by `rust/tests/web/issue-1154-command-argument.test.mjs` (8 tests passing locally, including the server entry). |
| R1154-2 | Invariant independent of parsing: never plan a tool call whose name and arguments are byte-identical to one already attempted in the current turn window; if the planner would, report the stuck step and its last result instead of repeating it. | Implemented: `Progress::repeated_call` (`rust/src/agentic_coding/progress.rs`, JS `Progress.repeatedCall` in `js/agentic/progress.mjs`) recognizes a completed call by byte-identical arguments or the same canonical command/URL operand (the protocol layer may project `command` onto `cmd` before the transcript echoes the call), and `stop_repeated_call` (`rust/src/agentic_coding/planner.rs`, JS `stopRepeatedCall`) replaces the repeat with the `stuck_step_report` answer from `data/meta/work-item-steps.lino`. A completed call is the loop signature; a failed one keeps its existing bounded retry and the two-failure stop of issue #1133. Pinned by `repeated_successful_read_is_reported_not_replanned` in `rust/tests/unit/agentic-coding/issue_1154_progress_arguments.rs` and by the R1154-2 cases of `rust/tests/web/issue-1154-command-argument.test.mjs`. |
| R1154-3 | After a successful read, the fetched text drives `plan_work_item_execution` exactly as on the Claude and Agent paths. | Implemented by the shared reading: `issue_view_url` resolves under `cmd` (and under a schema-declared key through R1154-1's projection), the read lands in `fetched_pages`, and `repository_work_item_objective` feeds `plan_work_item_execution` unchanged. Pinned by `codex_cmd_read_drives_execution_instead_of_repeating` in `rust/tests/unit/agentic-coding/issue_1154_progress_arguments.rs` and its JS twin in `rust/tests/web/issue-1154-command-argument.test.mjs`. |
| R1154-4 | Tests: replay the Codex transcript's first two Responses items (`function_call` `exec_command {"cmd": …}` + `function_call_output`) through the Responses input conversion and assert the next plan is not another `gh issue view`; a table test over `{command}`, `{cmd}`, `{script}`, `{command:[…]}` yields the same recorded read. | Implemented in `rust/tests/unit/agentic-coding/issue_1154_progress_arguments.rs`: the replay goes through `ResponsesRequest::to_chat_completion_request` (the server's own conversion), and the table covers all four spellings plus the twice-repeated transcript shape. |
