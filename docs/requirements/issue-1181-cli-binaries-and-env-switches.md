## Issue #1181 Standalone CLI Binaries and Consistent Boolean Env Switches

Issue [#1181](https://github.com/link-assistant/formal-ai/issues/1181) (E146,
part of the #1183 umbrella) has two halves: people cannot *run* the released
CLI at all (the release ships desktop apps and a VSIX but no standalone
`formal-ai` binary — the only channels are a full `cargo install` source build
or a 24.3 GB container image, #1153), and the one env switch that gates CLI
output rejects the conventional `1`/`0` spellings (`FORMAL_AI_SILENT=1
formal-ai chat …` fails with `invalid value '1' for '--silent' [possible
values: true, false]`). The evidence, the design, and the per-file change list
live in `docs/case-studies/issue-1181/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1181-1 | `.github/workflows/desktop-release.yml` gains a `cli` job that builds `formal-ai` for `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc` and uploads one archive per target to the same GitHub Release the `build`/`vscode` jobs publish to. | Implemented and tested as a mechanism: the `cli` job in `.github/workflows/desktop-release.yml` (five-leg matrix mirroring the `build` job's needs/concurrency/if/permissions/checkout/sccache conventions, `taiki-e/setup-cross-toolchain-action@v1` for the musl legs because the dependency graph compiles C code) uploads each archive with `gh release upload` to the tag `resolve` picked. `scripts/desktop-release-resolve.sh` now requires the archives of every `label: cli-*` matrix leg (read from the workflow, not a second list) before its idempotency guard skips a release, so a release that has the desktop set but lacks a CLI archive is rebuilt instead of staying partial. Pinned by `rust/tests/web/issue-1181-cli-release-assets.test.mjs` (the matrix is exactly the five requested targets; the resolver script, run with a recording `gh`, rebuilds a release without the CLI archives and skips a complete one) and by `workflow_run_builds_when_release_is_missing_cli_archives` in `rust/tests/unit/ci-cd/desktop_release_resolve.rs`. What only the next tagged release can show: its asset list carries the five `formal-ai-cli-*` archives, which needs the real cross-builds on the five runners. |
| R1181-2 | Each archive is named `formal-ai-cli-<target-triple>.tar.gz` (`.zip` for the Windows target), contains the `formal-ai` binary plus `LICENSE` and `README.md` under a top-level `formal-ai-cli-<triple>/` directory, and is reproducible from `cargo build --release --target <triple> --manifest-path rust/Cargo.toml --bin formal-ai --locked`. | Implemented and tested as a mechanism: the "Build formal-ai CLI binary" step runs the exact pinned-lock command; `rust/tests/web/issue-1181-cli-release-assets.test.mjs` executes the job's own "Package the CLI archive", "Smoke test CLI archive" and "Collect CLI checksum fragment" step scripts with a stand-in binary and asserts the archive holds `formal-ai`, `LICENSE` and `README.md` under `formal-ai-cli-<triple>/`, that the smoke test runs the extracted binary's `--version`, and that the fragment is one `sha256sum`-format line naming the archive. What only a release run can show: the real binaries for all five targets (the `.zip` leg runs PowerShell's archiver on the Windows runner). |
| R1181-3 | The `finalize` job's consolidated `SHA256SUMS.txt` and `BUILD-PROVENANCE.txt` cover the five CLI archives alongside the existing desktop/VSIX assets, in the same files, with the same "INCOMPLETE" honesty reporting for partial matrices. | Implemented and tested as a mechanism: `cli` joins `finalize`'s `needs`; each leg uploads a `SHA256SUMS-cli-<label>.partial` fragment (the `cli-` label prefix prevents collision with the desktop legs' identically-shaped labels in the merged `fragments/` directory); the `builder_of` map and label loop in `finalize` carry every `cli-*` label mapped to its runner. `rust/tests/web/issue-1181-cli-release-assets.test.mjs` checks the map and loop against the matrix and executes the finalize manifest step on a CLI fragment with a recording `gh`: the archive's line lands in `SHA256SUMS.txt`, `BUILD-PROVENANCE.txt` names its builder, and the legs that produced nothing are reported as `INCOMPLETE` with `incomplete=` in the step output. The consolidated files on a real release appear with the next tagged release. |
| R1181-4 | `rust/Cargo.toml` gains a `[package.metadata.binstall]` table so `cargo binstall formal-ai` resolves one of the R2 archives without a source build. | Implemented and tested: `[package.metadata.binstall]` (`pkg-url` …/`formal-ai-cli-{ target }.tar.gz`, `pkg-fmt "tgz"`, `bin-dir "formal-ai-cli-{ target }/{ bin }{ binary-ext }"`) with a `x86_64-pc-windows-msvc` override to the `.zip`; the URL is written out literally because the archive name ends `.tar.gz`, not binstall's default `{ archive-suffix }` (`.tgz`). `rust/tests/web/issue-1181-cli-release-assets.test.mjs` fills the templates for every matrix leg and asserts the URL is `releases/download/v<version>/<the archive the workflow uploads>`, the format matches the archive and `bin-dir` is the binary's path inside it. A real `cargo binstall formal-ai` resolves once the next tagged release carries the archives. |
| R1181-5 | `scripts/install.sh`'s `install_cli()` and `install.ps1`'s equivalent download and verify the matching `formal-ai-cli-<target>` archive first, falling back to `cargo install formal-ai` only when no matching archive exists for the host's OS/arch (e.g. windows-arm64, which R1 does not build). | Implemented and tested: `install_cli_prebuilt`/`Install-CliPrebuilt` resolve the host triple, fetch the archive, verify it against the release's `SHA256SUMS.txt` through the existing `verify_checksum`/`Test-Checksum` helpers, run the installed binary's `--version`, and only then report success; any unavailable/failed prebuilt path falls back to the unchanged `cargo install` body. `rust/tests/web/issue-1181-cli-release-assets.test.mjs` runs `scripts/install.sh cli` against a stand-in GitHub (recording `curl`, fixed `uname`, recording `cargo`) with the archive the workflow's package step built: it installs and runs the binary without calling `cargo`; a checksum mismatch aborts with nothing installed and no `cargo` fallback; a host no leg builds (Linux riscv64) falls back to `cargo install formal-ai` without downloading an archive. It also checks that both installers map hosts only to matrix targets, and parses `install.ps1` with PowerShell's parser where `pwsh` is installed (the Linux runner of `layered-ci.yml`; this macOS workstation has none, so the parse runs in CI only). |
| R1181-6 | A single boolean-env parser accepts `1/0/true/false/yes/no/on/off` case-insensitively (surrounding whitespace tolerated; anything else is unrecognised, never silently coerced), is the `value_parser` for every clap arg with `env = "FORMAL_AI_*"` on a `bool` field, and is used by every ad-hoc `std::env::var("FORMAL_AI_*")` boolean read in `rust/src`. | Delivered and tested: `rust/src/cli_env.rs` (`parse_bool_env`, `bool_env_value_parser`, `flag_enabled`, `flag_disabled`) wired into `rust/src/main.rs`'s `--silent` (the only clap bool arg with an `env` attribute in the crate) and into every ad-hoc boolean read — the full converted-site list is in `docs/case-studies/issue-1181/README.md`. `solver_helpers::env_bool`/`env_bool_with_extra_truthy` now delegate to the same table so there is one spelling vocabulary crate-wide. Pinned by `rust/tests/unit/issue_1181_boolean_environment_parser.rs`. The one intentional exception: `FORMAL_AI_FULL_TRUST` (`rust/src/bounded_autonomy.rs`) keeps its exact-`"1"` sentinel because it is a security opt-in, not a UX switch. `rust/src/translation/pipeline.rs`'s `FORMAL_AI_TRANSLATION_DEBUG` read is deferred to the issue-#1174 change that owns that file. |
| R1181-7 | `FORMAL_AI_SILENT=1 formal-ai chat --prompt …` (and `=true`, `=yes`, `=on`, case-insensitive, and their false-y counterparts) no longer errors, and the non-clap `verbose_enabled()` read of the same variable honours the same spellings. | Delivered and tested: the `value_parser = formal_ai::cli_env::bool_env_value_parser` attribute on `--silent` (the `SetTrue` action is preserved, so a bare `--silent` flag still works), and `dialog_log::verbose_enabled()`'s second read goes through `!flag_enabled("FORMAL_AI_SILENT")`. Pinned by `silent_switch_now_accepts_one_as_the_issue_reported` and `bool_env_value_parser_maps_spellings_to_clap_results` in the same test file, which assert the exact truth table for the reported failing value. |
