## Issue #1181 Standalone CLI Binaries and Consistent Boolean Env Switches

Issue [#1181](https://github.com/link-assistant/formal-ai/issues/1181) (E146,
part of the #1183 umbrella) has two halves: people cannot *run* the released
CLI at all (the release ships desktop apps and a VSIX but no standalone
`formal-ai` binary — the only channels are a full `cargo install` source build
or a 24.3 GB container image, #1153), and the one env switch that gates CLI
output rejects the conventional `1`/`0` spellings (`FORMAL_AI_SILENT=1
formal-ai chat …` fails with `invalid value '1' for '--silent' [possible
values: true, false]`). The evidence, the design, and the per-file change list
live in `docs/case-studies/issue-1181/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1181-1 | `.github/workflows/desktop-release.yml` gains a `cli` job that builds `formal-ai` for `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc` and uploads one archive per target to the same GitHub Release the `build`/`vscode` jobs publish to. | Delivered as workflow: the `cli` job in `.github/workflows/desktop-release.yml` (five-leg matrix mirroring the `build` job's needs/concurrency/if/permissions/checkout/sccache conventions, `taiki-e/setup-cross-toolchain-action@v1` for the musl legs because the dependency graph compiles C code). Observable on the next tagged release, whose asset list must show the five `formal-ai-cli-*` archives; until then it is code-reviewed, not executed. |
| R1181-2 | Each archive is named `formal-ai-cli-<target-triple>.tar.gz` (`.zip` for the Windows target), contains the `formal-ai` binary plus `LICENSE` and `README.md` under a top-level `formal-ai-cli-<triple>/` directory, and is reproducible from `cargo build --release --target <triple> --manifest-path rust/Cargo.toml --bin formal-ai --locked`. | Delivered as workflow: the "Package the CLI archive" and "Smoke test CLI archive" steps build with the exact pinned-lock command, package the staging directory, then extract the archive on the leg's own runner and run `./formal-ai --version` plus non-emptiness checks on `LICENSE`/`README.md`. |
| R1181-3 | The `finalize` job's consolidated `SHA256SUMS.txt` and `BUILD-PROVENANCE.txt` cover the five CLI archives alongside the existing desktop/VSIX assets, in the same files, with the same "INCOMPLETE" honesty reporting for partial matrices. | Delivered as workflow: `cli` joins `finalize`'s `needs`; each leg uploads a `SHA256SUMS-cli-<label>.partial` fragment (the `cli-` label prefix prevents collision with the desktop legs' identically-shaped labels in the merged `fragments/` directory); the `builder_of` map and label loop in `finalize` gain the five `cli-*` labels mapped to their runners. |
| R1181-4 | `rust/Cargo.toml` gains a `[package.metadata.binstall]` table so `cargo binstall formal-ai` resolves one of the R2 archives without a source build. | Delivered: `[package.metadata.binstall]` (`pkg-url` …/`formal-ai-cli-{ target }.tar.gz`, `pkg-fmt "tgz"`, `bin-dir "formal-ai-cli-{ target }/{ bin }{ binary-ext }"`) with a `x86_64-pc-windows-msvc` override to the `.zip`; the URL is written out literally because the archive name ends `.tar.gz`, not binstall's default `{ archive-suffix }` (`.tgz`). Executed only when the first release carrying the assets exists. |
| R1181-5 | `scripts/install.sh`'s `install_cli()` and `install.ps1`'s equivalent download and verify the matching `formal-ai-cli-<target>` archive first, falling back to `cargo install formal-ai` only when no matching archive exists for the host's OS/arch (e.g. windows-arm64, which R1 does not build). | Delivered: `install_cli_prebuilt`/`Install-CliPrebuilt` resolve the host triple, fetch the archive, verify it against the release's `SHA256SUMS.txt` through the existing `verify_checksum`/`Test-Checksum` helpers, run the installed binary's `--version`, and only then report success; any unavailable/failed prebuilt path falls back to the unchanged `cargo install` body. A checksum mismatch still aborts (it never falls back silently). `install.ps1` could not be machine-parsed on this macOS workstation (no PowerShell); it follows the file's existing cmdlet idioms and is review-verified. |
| R1181-6 | A single boolean-env parser accepts `1/0/true/false/yes/no/on/off` case-insensitively (surrounding whitespace tolerated; anything else is unrecognised, never silently coerced), is the `value_parser` for every clap arg with `env = "FORMAL_AI_*"` on a `bool` field, and is used by every ad-hoc `std::env::var("FORMAL_AI_*")` boolean read in `rust/src`. | Delivered and tested: `rust/src/cli_env.rs` (`parse_bool_env`, `bool_env_value_parser`, `flag_enabled`, `flag_disabled`) wired into `rust/src/main.rs`'s `--silent` (the only clap bool arg with an `env` attribute in the crate) and into every ad-hoc boolean read — the full converted-site list is in `docs/case-studies/issue-1181/README.md`. `solver_helpers::env_bool`/`env_bool_with_extra_truthy` now delegate to the same table so there is one spelling vocabulary crate-wide. Pinned by `rust/tests/unit/issue_1181_boolean_env_parser.rs`. The one intentional exception: `FORMAL_AI_FULL_TRUST` (`rust/src/bounded_autonomy.rs`) keeps its exact-`"1"` sentinel because it is a security opt-in, not a UX switch. `rust/src/translation/pipeline.rs`'s `FORMAL_AI_TRANSLATION_DEBUG` read is deferred to the issue-#1174 change that owns that file. |
| R1181-7 | `FORMAL_AI_SILENT=1 formal-ai chat --prompt …` (and `=true`, `=yes`, `=on`, case-insensitive, and their false-y counterparts) no longer errors, and the non-clap `verbose_enabled()` read of the same variable honours the same spellings. | Delivered and tested: the `value_parser = formal_ai::cli_env::bool_env_value_parser` attribute on `--silent` (the `SetTrue` action is preserved, so a bare `--silent` flag still works), and `dialog_log::verbose_enabled()`'s second read goes through `!flag_enabled("FORMAL_AI_SILENT")`. Pinned by `silent_switch_now_accepts_one_as_the_issue_reported` and `bool_env_value_parser_maps_spellings_to_clap_results` in the same test file, which assert the exact truth table for the reported failing value. |
