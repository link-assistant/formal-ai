## Issue #1187 Optional GitHub Credentials in Every Workflow

Issue [#1187](https://github.com/link-assistant/formal-ai/issues/1187) (E151,
part of the E127 umbrella #1183): tokens are "not mandatory, but optional in
all cases". One resolver chooses a GitHub App, then one `AUTOMATION_TOKEN`
secret, then `github.token`; bot pull requests get their checks by dispatch
instead of waiting for approval; isolated tests use orphan branches in this
repository; cross-repository work degrades to a report. R1187-1 through
R1187-6 are the issue's R1–R6; R1187-7 and R1187-8 are its automated and
manual tests. Existing-file migrations are deferred edits recorded in
`docs/integration-manifest.md`; the history and the #1124 check evidence
live in `docs/case-studies/issue-1187/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1187-1 | Every workflow that writes to GitHub takes its token from one resolver — GitHub App (`AUTOMATION_APP_ID` + `AUTOMATION_APP_PRIVATE_KEY`) → `AUTOMATION_TOKEN` → `github.token`; `FORMAL_AI_BOT_TOKEN` is replaced; nothing skips or fails on a missing token; the layer is printed to the log and the job summary. | Implemented: `.github/actions/automation-token/action.yml` resolves the three layers, writes the layer to the log and `GITHUB_STEP_SUMMARY`, and exposes `can-create-repositories` (true only at the App layer); `cross-org-duplication.yml`, `dependencies-latest.yml`, `e2e-isolation.yml` and now `self-authored-pull-request.yml` use it. The self-authored job no longer reads `secrets.FORMAL_AI_BOT_TOKEN`: it passes the resolved token as `GH_TOKEN` and, for the composite action's unchanged contract, as `FORMAL_AI_BOT_TOKEN` only when the layer is not `default`. `release.yml` reads no `FORMAL_AI_BOT_TOKEN`. Pinned by `the_resolver_action_implements_the_three_layers`, `no_workflow_or_action_reads_a_github_token_secret_but_the_automation_names` and `the_self_authored_workflow_resolves_its_token_and_dispatches_checks` in `rust/tests/unit/issue_1187_credentials.rs`. The action is a local mirror of link-foundation/.github `resolve-github-token` (link-foundation/.github#1), not a call to it. |
| R1187-2 | At layer `default`, the workflow that opened or pushed the pull request dispatches every `pull_request` workflow on the head commit; `layered-ci.yml`, `evidence-check.yml` and `workflows.yml` gain `workflow_dispatch` with `mode: checks`. | Partial: `self-authored-pull-request.yml` calls `.github/actions/dispatch-checks` at layer `default` once the bot pull request exists. The dispatcher runs `gh workflow run` on the pull request's head branch (the dispatch API takes a ref, not a sha) for every `pull_request` workflow that declares the checks mode (`options: [checks]`), and warns on the rest. `layered-ci.yml`, `evidence-check.yml`, `workflows.yml` and `web-ui-boundary.yml` gain `workflow_dispatch` with a `mode` choice of `checks` and a `pull-request` input. Pinned by `the_dispatcher_dispatches_pull_request_workflows`, `every_pull_request_workflow_is_dispatchable_and_ignores_e2e_bases`, `the_named_workflows_declare_the_checks_mode_the_dispatcher_passes` and `the_self_authored_workflow_resolves_its_token_and_dispatches_checks` in `rust/tests/unit/issue_1187_credentials.rs`. The other `pull_request` workflows have no checks mode, so they are warned about and not dispatched; whether the dispatched runs satisfy branch protection is unverified (R1187-8). |
| R1187-3 | `release.yml` gets a checks-only dispatch mode that is the default, and every release, publish and tag job requires an explicit release mode and `github.ref == 'refs/heads/main'`. | Implemented 2026-10-07: `release.yml`'s `workflow_dispatch` declares the checks-mode `mode` input (`options: [checks]`, so `actions/dispatch-checks` may dispatch it) and a `release_mode` that defaults to `checks` (`bump_type` defaults to `patch`); `manual-release`, `changelog-pr`, the Pages deploy and the release preflight's release mode each require an explicit `instant` or `changelog-pr` mode and `github.ref == 'refs/heads/main'`, and `detect-changes` names its push and pull-request triggers instead of excluding dispatch. A checks dispatch runs only the lint and test jobs. Pinned by `release_dispatch_needs_an_explicit_mode_and_main_or_a_pending_row` in `rust/tests/unit/issue_1187_credentials.rs`, which now passes on the guard itself rather than on a pending manifest row. |
| R1187-4 | Workloads needing a separate test tree use an orphan branch `e2e/<purpose>/<run_id>/<name>` built with `git checkout --orphan`, an `e2e-task` issue and a pull request based on that branch, all closed and deleted at the end; a separate repository only when the resolver reports `can-create-repositories: true`; this repository's `pull_request` workflows ignore `e2e/**` bases. | Partial: `.github/workflows/e2e-isolation.yml` builds the orphan branch from only the named paths, opens the `e2e-task` issue and the pull request, and its cleanup job closes both and deletes the branches, pinned by `orphan_branch_isolation_needs_no_credential`. Every `pull_request` workflow now carries `branches-ignore: ['e2e/**']`, pinned by `every_pull_request_workflow_is_dispatchable_and_ignores_e2e_bases` in `rust/tests/unit/issue_1187_credentials.rs`. It always uses the orphan branch: there is no separate-repository path even at the App layer. |
| R1187-5 | Cross-repository work opens issues directly at layer `app`/`token` when it can write there; at layer `default` it writes findings to its report and keeps one tracking issue in this repository. | Partial: `.github/workflows/cross-org-duplication.yml` drops `--open` at layer `default` with a `::warning::` and uploads `data/meta/cross-org-duplication.lino` as the report. It does not file or update a tracking issue in this repository, and no #1179 workload exists yet. No unit test asserts this branch. |
| R1187-6 | `CONTRIBUTING.md` gains a "GitHub credentials" section: the three layers, `AUTOMATION_TOKEN` as the only token name, the optional GitHub App, and that nothing needs configuring. | Implemented: the "GitHub credentials" section of `CONTRIBUTING.md`, pinned by `contributing_states_the_credential_rules` in `rust/tests/unit/issue_1187_credentials.rs`. The section's claim that the unit test fails on any other token secret name now holds: `no_workflow_or_action_reads_a_github_token_secret_but_the_automation_names` rejects every `secrets.*` GitHub credential outside the `AUTOMATION_*` names. |
| R1187-7 | An automated test parses every workflow and composite action and fails on a GitHub-token secret other than the two `AUTOMATION_*` names, on a `pull_request` workflow without `workflow_dispatch`, and on a release job that can run on dispatch without an explicit mode and the `main` ref. | Implemented with one tolerated exception: `rust/tests/unit/issue_1187_credentials.rs` (at that path, not under `ci_cd/` as the issue named it) parses every workflow and composite action and fails on a GitHub-token secret other than the `AUTOMATION_*` names (`no_workflow_or_action_reads_a_github_token_secret_but_the_automation_names`), on a `pull_request` workflow without `workflow_dispatch` or without the `e2e/**` ignore (`every_pull_request_workflow_is_dispatchable_and_ignores_e2e_bases`), and on a `release.yml` dispatch branch without an explicit mode and the `main` ref (`release_dispatch_needs_an_explicit_mode_and_main_or_a_pending_row`). The release rule still finds two unguarded lines and passes only while the pending R1187-3 row in `docs/integration-manifest.md` exists; `every_pending_manifest_row_names_a_file_and_an_issue` keeps that row honest. |
| R1187-8 | Manual acceptance: with no `AUTOMATION_*` configured, labelling an issue `formal-ai-solve` produces a bot pull request whose checks all start without approval, and the summary reads `layer default`. | Pending: not run. The workflow side (R1187-1, R1187-2) is now in place; the acceptance run needs an issue labelled `formal-ai-solve` on a repository with no `AUTOMATION_*` configured. |
