## Issue #1175 Routing by Formalization, Not by a Surface Word

Issue [#1175](https://github.com/link-assistant/formal-ai/issues/1175) (E140,
part of the #1183 umbrella) stops two intent detectors from claiming a prompt
because a single word matched a recognition surface: the terminal-command
detector fired whenever a prompt's first word was a seed shell token, and the
software-project detector picked its artifact kind from an artifact surface
anywhere in the prompt. The source analysis, the before/after evidence, and
the honest boundaries live in `docs/case-studies/issue-1175/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1175-1 | The leading-token path of terminal-command detection claims a prompt only when the words after the leading shell token parse as command arguments: no question mark (ASCII or full-width), no colon followed by a space outside quotes, no bare token ending in sentence punctuation (except a token that is entirely dots — `.` and `..` are paths), and no bare function word from a small closed marker list; quoted spans are masked before every check, so prose inside quotes is data. Command shapes stay accepted, including `find . -name '*.log' -size +10M`, `make test`, `head -n 5 main.rs`, `export FOO=bar`, `touch newfile.txt`, `git commit -m 'fix the parser bug'`, and single bare tokens; the backtick+verb and verb+phrase trigger paths are unchanged. | Implemented in `rust/src/solver_terminal.rs` (`parses_as_command_arguments` with `mask_quoted_spans` and `NATURAL_LANGUAGE_MARKER_WORDS`, gated into `leading_shell_command`); JavaScript twin in `js/worker/formal_ai_worker_09.js` (`parsesAsCommandArguments` with `maskQuotedSpans`). Pinned by `rust/tests/unit/issue_1175_routing.rs`. |
| R1175-2 | The software-project handler selects its artifact kind only from the head noun of the object phrase governed by the authoring verb — the first boundary-delimited segment after the verb (benefactives and determiners skipped), or, for a verb-final (subject-object-verb) request with nothing after the verb, the last segment before it — never from an artifact word elsewhere in the prompt. Artifact-headed requests keep the frame in every lexicalised language, including unspaced CJK. | Implemented in `rust/src/solver_handlers/software_project.rs` (`object_phrase_artifact` with `skip_object_phrase_lead`, `object_phrase_segments`, `boundary_cut`, `match_artifact_head`, `scan_action_from`; the old any-position `match_artifact`/`scan_match` are deleted; `software_project_claims` and `from_prompt` both route through the new analysis). Pinned by `rust/tests/unit/issue_1175_routing.rs`. |
| R1175-3 | Routing is decided by a full capability-table refactor so no handler can claim on a surface match alone. | Partial: this change delivers the targeted guards at the two reported detection sites and pins them with held-out probes; the wholesale capability-table refactor of every handler's claims is not delivered here and remains open. |
| R1175-4 | A 200-prompt CI routing probe set covers every intent lane with a coverage budget, so a misroute of this class cannot land unnoticed. | Partial: 24 held-out routing probes (en, ru, hi, zh — including the three reported prompts, five prose-starting-with-a-shell-word prompts, seven command shapes, and five incidental-artifact prompts) are delivered in `rust/tests/unit/issue_1175_routing.rs`, each verified absent from `data/seed/`; the 200-prompt set with per-intent coverage budgeting is not. |
| R1175-5 | Three-roots parity: the browser worker's terminal detection and software-project detection follow the same rules. | Partial: the terminal-detection guard is mirrored in `js/worker/formal_ai_worker_09.js` and its regenerated `ts/worker/formal_ai_worker_09.ts` twin (syntax-checked; the `ts/` tree was regenerated by the pull-request integrator). The software-project guard's JavaScript twin is open — no `objectPhraseArtifact` equivalent exists in `js/worker/` — so the browser worker's software-project detection still matches artifact words at any position. |
