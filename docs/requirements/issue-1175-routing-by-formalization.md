## Issue #1175 Routing by Formalization, Not by a Surface Word

Issue [#1175](https://github.com/link-assistant/formal-ai/issues/1175) (E140,
part of the #1183 umbrella) stops two intent detectors from claiming a prompt
because a single word matched a recognition surface: the terminal-command
detector fired whenever a prompt's first word was a seed shell token, and the
software-project detector picked its artifact kind from an artifact surface
anywhere in the prompt. The source analysis, the before/after evidence, and
the honest boundaries live in `docs/case-studies/issue-1175/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1175-1 | The leading-token path of terminal-command detection claims a prompt only when the words after the leading shell token parse as command arguments: no question mark (ASCII or full-width), no colon followed by a space outside quotes, no bare token ending in sentence punctuation (except a token that is entirely dots — `.` and `..` are paths), and no bare function word from a small closed marker list; quoted spans are masked before every check, so prose inside quotes is data. Command shapes stay accepted, including `find . -name '*.log' -size +10M`, `make test`, `head -n 5 main.rs`, `export FOO=bar`, `touch newfile.txt`, `git commit -m 'fix the parser bug'`, and single bare tokens; the backtick+verb and verb+phrase trigger paths are unchanged. | Implemented in `rust/src/solver_terminal.rs` (`parses_as_command_arguments` with `mask_quoted_spans` and `NATURAL_LANGUAGE_MARKER_WORDS`, gated into `leading_shell_command`); JavaScript twin in `js/worker/formal_ai_worker_09.js` (`parsesAsCommandArguments` with `maskQuotedSpans`). Pinned by `rust/tests/unit/issue_1175_routing.rs`. |
| R1175-2 | The software-project handler selects its artifact kind only from the head noun of the object phrase governed by the authoring verb — the first boundary-delimited segment after the verb (benefactives and determiners skipped), or, for a verb-final (subject-object-verb) request with nothing after the verb, the last segment before it — never from an artifact word elsewhere in the prompt. Artifact-headed requests keep the frame in every lexicalised language, including unspaced CJK. | Implemented in `rust/src/solver_handlers/software_project.rs` (`object_phrase_artifact` with `skip_object_phrase_lead`, `object_phrase_segments`, `boundary_cut`, `match_artifact_head`, `scan_action_from`; the old any-position `match_artifact`/`scan_match` are deleted; `software_project_claims` and `from_prompt` both route through the new analysis). Pinned by `rust/tests/unit/issue_1175_routing.rs`. |
| R1175-3 | Routing is decided by a full capability-table refactor so no handler can claim on a surface match alone. | Partial: this change delivers the targeted guards at the two reported detection sites and pins them with held-out probes; the wholesale capability-table refactor of every handler's claims is not delivered here and remains open. Re-checked 2026-10-07: still partial. New routes follow the rule without the table — the #1180 `repository_lineage` route claims only when its cue and an existing repository path are both present — but the shell-command and software-artifact rows of `data/seed/capability-routing.lino`, and the router consulted after formalization before the handler table, do not exist yet. Re-checked 2026-10-07 (fourth pass): the router and the table now exist. The `claim` rows of `data/seed/capability-routing.lino` (registered as a web seed) name a handler, its browser function and the structural evidence kinds that admit it: `software_project` on `object_phrase_artifact` or `approval_of_a_proposal`, `terminal_command` on `shell_command_shape` or `semantic_shell_task`, `repository_lineage` on `repository_subject`. `rust/src/capability_routing/claims.rs` (`claim_admitted`) is consulted by `meta_method_dispatch::try_dispatch` before each handler and by the solver's terminal-command fallback; `claimRouteAdmits` in `js/worker/formal_ai_worker_dispatch.js` is the browser twin, consulted before each synchronous handler. A handler with no row is admitted as before. Pinned by `rust/tests/unit/issue_1175_claim_routing.rs` and `rust/tests/web/issue-1175-claim-routing.test.mjs`; `rust/tests/web/r1175-routing-probes.test.mjs` and the `js_misroute_ceiling` still hold. Still partial: three handlers carry rows; moving every other handler's claim into a row is what stays open. |
| R1175-4 | A 200-prompt CI routing probe set covers every intent lane with a coverage budget, so a misroute of this class cannot land unnoticed. | Implemented 2026-10-07 for every single-turn lane: 359 held-out probes (256 en, 65 ru, 17 hi, 21 zh; 57 adversarial prose that surface-matches another lane, such as line counts over shell commands and JSON-to-YAML conversions whose keys say `lines`/`count`) in `rust/tests/fixtures/routing-probes/probes-*.lino`, each naming its lane, language and the intent the system should answer. `budget.lino` sets the coverage budget over the 105 shared lanes (every row of `data/seed/handler-precedence.lino`, every slug of `data/seed/intent-routing.lino`, plus the terminal-command detector): 85 lanes carry at least 2 probes; 20 lanes are exempt with a stated reason (10 `browser_only` memory/context rows and 10 follow-up lanes that need an earlier turn), and an exemption for a covered lane fails. The browser worker runs every probe in `rust/tests/web/r1175-routing-probes.test.mjs`; the native solver (offline) in `rust/tests/unit/issue_1175_routing_probes.rs`. Misroutes found while building the corpus are not fixed here: they are ratchets (`js_misroute`, 118 probes, `js_misroute_ceiling 118`; `rust_misroute unverified`, 75 probes the native answer is not yet pinned on, `rust_misroute_ceiling 75`) — a new misroute fails, a fixed browser misroute fails until its line is removed and the ceiling lowered, and the ceilings must equal the listed counts. Boundary: the native test was written without a local cargo run, so its strict set (284 probes) is confirmed by CI, not here. |
| R1175-5 | Three-roots parity: the browser worker's terminal detection and software-project detection follow the same rules. | Implemented 2026-10-07: the terminal-detection guard is mirrored in `js/worker/formal_ai_worker_09.js`, and the software-project guard in `detectSoftwareObjectPhrase` (`js/worker/formal_ai_worker_11.js`, over the shared `objectPhraseArtifact`), so the browser reads the artifact from the request's object phrase as Rust does; `ts/` is regenerated from both. Pinned by `rust/tests/web/issue-1175-software-object-phrase.test.mjs`. |
