## Issue #559 General Meta Algorithm

Issue [#559](https://github.com/link-assistant/formal-ai/issues/559) asks to
generalize the solver away from hardcoded specific intents toward a single
general meta algorithm: translate every message into the meta language, detect
all questions/requirements/needs, address each in the answer, and let the core
reason about its own method set and review-gated improvements. PR
[#560](https://github.com/link-assistant/formal-ai/pull/560) lands the live
registry-backed meta method path plus the link-native audit artifacts. The full
plan, requirements derivation, recursive core, and option comparison are in
`docs/case-studies/issue-559/`. New rows
R330–R344 capture obligations genuinely new to this issue; most of #559 is
realized through existing rows (R72/R74/R97/R103/R157/R158/R67/R264/R311/R314/R129).
Those rows completed the registry-backed route-authority slice, not the removal
of intent-specific handler implementations. Issue #699 tracks that remaining
migration honestly in `data/meta/handler-migration-ledger.lino`.

| R341 | The hardcoded natural-language cue lists that drive the meta core's intent recognition must move out of inline Rust literals into first-class, reviewable link data: each cue belongs to a named cue set declaring how it is matched (`token` whitespace-bounded word / CJK substring, `substring` raw contains, or `prefix` starts-with), and the Rust call sites read the cue strings from that data while keeping only the structural glue (digit presence, AND/OR composition, which input each set is tested against).
