# Issue #1155: Work-Item Read Validation and Honest Fallbacks

Issue [#1155](https://github.com/link-assistant/formal-ai/issues/1155) (E120):
an unauthenticated `gh issue view` printed its how-to-authenticate banner, the
Agent CLI echoed that output with the exit status dropped (`"metadata":
{"exit": 4}` in its own record, plain text in the tool message Formal AI
received), and the banner was accepted as the issue body. The run then wrote
`.formal-ai/general-change-plan.lino` and answered `planned_not_executed`
without ever trying the `webfetch` tool the client offered. The full account,
with the transcript excerpts, is `docs/case-studies/issue-1155/`.

| ID | Requirement | Status / Evidence |
| --- | --- | --- |
| R1155-1 | The read observes its own status whatever the client sends: the planned read ends with `printf '\n__formal_ai_exit=%s\n' $?`, as data in `data/meta/work-item-steps.lino` (`issue_view_command`), and a non-zero status is a failed read. | Implemented: `issue_view_command` in `data/meta/work-item-steps.lino` (and the byte-identical embedded mirror) now appends the sentinel `printf`; `exit_sentinel` (`rust/src/agentic_coding/progress.rs`) reads the last `__formal_ai_exit=N` line and `work_item_read_failure_reason` turns any non-zero status into a failed read even when the client's echo carries no error flag. JavaScript root (2026-10-07): the twins in `js/agentic/progress.mjs` and `js/agentic/general_execution.mjs` behave the same, and `composeRepositoryWorkPlan` (`js/agentic/general_planner.mjs`) now accepts an objective that opens with the work-item reference, as the Rust `opens_with_reference` does; without it the JavaScript planner never reached the read and fetched the issue page through the generic capability route instead. Pinned by `rust/tests/unit/agentic-coding/issue_1155_read_validation.rs` and `rust/tests/web/issue-1155-read-validation.test.mjs`. |
| R1155-2 | The read's shape is validated before it is accepted as the issue: a title line, a blank separator, then the body — output without that shape is a failed read, recorded with its text. | Implemented: `work_item_read_failure_reason` requires the `gh` reads to contain the blank-line separator (the incident banner has none) and the raw-body `curl` read to be non-empty text that does not begin like the API's JSON error blob; failed reads land in `Progress::failed_work_item_reads` with their reason and are never pushed to `fetched_pages`. Pinned by `a_status_less_gh_banner_is_a_failed_read_and_webfetch_of_the_issue_follows` and `a_failing_sentinel_outranks_a_well_shaped_output`. Pinned in both roots by `rust/tests/unit/agentic-coding/issue_1155_read_validation.rs` and `rust/tests/web/issue-1155-read-validation.test.mjs`. |
| R1155-3 | On a failed read, walk the fallbacks in order and record each attempt: the client's fetch tool on the issue URL, `curl -fsSL https://api.github.com/repos/<owner>/<repo>/<issues|pulls>/<n>`, `gh api`, then the prepared PR's title and body. | Implemented: `plan_work_item_read` (`rust/src/agentic_coding/general_execution.rs`) now plans, after the failed `gh` view: the fetch tool on the issue URL, `issue_rest_read_command` (credential-free `curl` with the raw-body `Accept` header), `issue_api_read_command` (two `gh api` calls printing title and body), and last `prepared_pull_reference` — the pull request the prompt names, fetched as page context. Pull-request work items read their REST `pulls/` endpoint. Every attempt is recorded; `Progress::work_item_read_attempts` lists them. Pinned by `the_rest_routes_follow_the_fetch_fallback_in_order`, `the_rest_fallback_of_a_pull_request_reads_the_pulls_endpoint`, `the_prepared_pull_request_is_the_last_read_fallback`. Pinned in both roots by `rust/tests/unit/agentic-coding/issue_1155_read_validation.rs` and `rust/tests/web/issue-1155-read-validation.test.mjs`. |
| R1155-4 | Only when all routes fail is `planned_not_executed` honest: the answer lists every read tried with its result, and the only write is never spent on the plan record when the goal could not be read. | Implemented: `work_item_read_failure_report` (filled from the `read_failed_report` data key) closes the run with every read, its reason and its first answer line — and `general_change_step` returns it before the `PLAN_PATH` write, so no plan record is written for an issue the session never read. Pinned by `an_exhausted_retrieval_reports_every_read_and_writes_no_plan_record`. Pinned in both roots by `rust/tests/unit/agentic-coding/issue_1155_read_validation.rs` and `rust/tests/web/issue-1155-read-validation.test.mjs`. |
| R1155-5 | Replay test from the transcript: with the Agent tool list (`webfetch`) and the `gh` result without exit status, the next plan is the `webfetch` of the issue URL; with the sentinel line `__formal_ai_exit=4` the read is a failure. | Implemented in `rust/tests/unit/agentic-coding/issue_1155_read_validation.rs` (the file name the dispatch directed; the issue's Definition of Done names `issue_1155_work_item_read_failure.rs` — same tests, rename at registration if preferred): `a_status_less_gh_banner_is_a_failed_read_and_webfetch_of_the_issue_follows` replays the status-less echo, `with_the_sentinel_line_the_read_is_a_failure_and_the_fetch_follows` replays it with `__formal_ai_exit=4`, and both assert the next plan is the `webfetch` of the issue URL. |
