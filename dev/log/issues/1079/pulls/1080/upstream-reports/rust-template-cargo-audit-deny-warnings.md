# Upstream report 3 - `cargo audit --file Cargo.lock` cannot fail on a yanked or unmaintained crate

**Target:** `link-foundation/rust-ai-driven-development-pipeline-template`

**Severity:** the dependency-audit gate is green by construction for an entire
class of finding, including yanked releases -- which are frequently yanked
*because* of a security problem.

---

## Title

The `Audit committed Cargo.lock` step exits 0 on `unmaintained`, `unsound` and
`yanked` findings; `--deny warnings` is what makes the gate a gate

## Affected site

`.github/workflows/security.yml:31-32` at
`4d444d976f6bb46168b9f4a7001c775bf7c0ef6b`:

```yaml
      - name: Audit committed Cargo.lock
        run: cargo audit --file Cargo.lock
```

## Root cause

`cargo audit` splits its findings in two. *Vulnerabilities* move the exit
status. *Warnings* -- which is how it classifies `unmaintained`, `unsound` and
`yanked` -- do not. They print, the step logs them, and the job goes green:

```
warning: 2 allowed warnings found
```

"allowed" is the operative word. Without `--deny warnings` the tool is
explicitly told that warnings are acceptable, so the step reports a passing
audit while displaying findings nobody will read, because nobody reads the log
of a green step.

`yanked` deserves separate mention. A yanked release is one the authors
withdrew, and the reasons include "we shipped a vulnerability". It carries no
advisory ID, which has a consequence worth knowing before it bites: it cannot
be silenced by an `[advisories] ignore` entry, only by `--no-yanked`, which
turns the whole check off. Yank findings must always be fixed in the lockfile,
and that is a good property -- but only once something makes them fatal.

## Reproducible example

Self-contained; no project needed. `cargo-audit` 0.22.2, the exact version the
template installs:

```console
$ mkdir yanked-repro && cd yanked-repro
$ cat > Cargo.lock <<'EOF'
# This file is automatically @generated by Cargo.
# It is not intended for manual editing.
version = 3

[[package]]
name = "demo"
version = "0.1.0"
dependencies = ["chacha20", "fxhash"]

[[package]]
name = "chacha20"
version = "0.10.1"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "3613f74bd2eac03dad61bd53dbe620703d4371614fe0bc3b9f04dd36fe4e818a"

[[package]]
name = "fxhash"
version = "0.2.1"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "c31b6d751ae2c7f11320402d34e41349dd1016f8d5d45e48c4312bc8625af50c"
EOF
```

The template's command:

```console
$ cargo audit --file Cargo.lock
Crate:     fxhash
Version:   0.2.1
Warning:   unmaintained
Title:     fxhash - no longer maintained
ID:        RUSTSEC-2025-0057

Crate:     chacha20
Version:   0.10.1
Warning:   yanked

warning: 2 allowed warnings found
$ echo $?
0
```

One flag, nothing else changed:

```console
$ cargo audit --file Cargo.lock --deny warnings
...
error: 2 denied warnings found!
$ echo $?
1
```

## This is currently latent in the template, and was not latent downstream

The template's own lockfile is clean today -- 45 crates, no findings either way
-- so nothing is broken right now. That is exactly why it is worth fixing now:
the gate will report success the first time it matters, and there will be no
signal that anything changed.

`link-assistant/formal-ai` adopted this workflow and hit it. `Cargo.lock`
pinned `chacha20 0.10.1`, a yanked release, and carried `fxhash 0.2.1`
unmaintained, and the Security workflow was green for the entire period.
Both findings are the two in the reproduction above; they were found by
reading the log of a passing job, which is not a process that scales.

## Suggested fix

```diff
       - name: Audit committed Cargo.lock
-        run: cargo audit --file Cargo.lock
+        # `unmaintained`, `unsound` and `yanked` are *warnings*, and a warning
+        # does not move `cargo audit`'s exit status -- it prints
+        # "warning: N allowed warnings found" and exits 0. Without this flag the
+        # step reports a passing audit while displaying the findings.
+        run: cargo audit --file Cargo.lock --deny warnings
```

## If that turns out to be too strict: the honest way to hold an exception

`--deny warnings` will eventually fail on something a repository genuinely
cannot fix that week -- a transitive dependency's unmaintained crate with no
patched version. The tempting response is a permanent `[advisories] ignore`
entry in `.cargo/audit.toml`, and a permanent ignore is a gate that has quietly
been switched off.

`link-assistant/formal-ai` handles this by requiring every ignore to carry a
machine-checkable proof line that expires on its own. There are two, and they
expire in opposite directions:

```toml
# RUSTSEC-XXXX-NNNN unreachable = "crate@version"
# RUSTSEC-XXXX-NNNN blocked-upstream = "crate@version" report = "https://github.com/owner/repo/issues/N"
```

A wrapper script re-derives each with
`cargo tree --locked --target all --all-features --edges all --invert <spec>`
before handing the lockfile to `cargo audit`. `unreachable` fails the moment
the crate *enters* the build graph. `blocked-upstream` fails the moment it
*leaves* -- which is precisely when the upstream fix landed and the entry has
become a lie -- and it will not accept the words "someone should fix this
upstream" in place of a URL to a filed issue.

Neither form can be written to mean "ignore this forever", which is the only
property that matters. The script is ~150 lines of bash and is offered freely
if it is useful:
<https://github.com/link-assistant/formal-ai/blob/main/scripts/check-rust-dependencies.sh>
