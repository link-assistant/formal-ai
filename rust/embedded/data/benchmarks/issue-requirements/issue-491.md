Once we will have fully real thinking steps we can start to optimize for least action.

For example if we some how find a way to do reasoning for a smaller number of steps, that will make each our reasoning path much shorter and more efficient.

To simplify the optimization, we should try from the start produce for each task split into 2 sub tasks. Meaning on the highest level of abstraction there is always 1, 2, 4, 8 and so on tasks.

So the balanced tree of sub tasks always preserved, but the thing we actually optimizing for is the total number of smallest sub task. And in real life, some tasks on 8 task level can have devisions, some of them already atomic and can have known solutions.

That also may mean shortest path or shortest steps to results, or shortest code (that still solves the entire range of inputs) when simplifying the code.

So when multiple solutions are generated, we can use least action or shortest path/steps to evaluate/score solutions.

That also may help in generalization and self/auto learning/improvement, to provide ways to handle the unhandled paths in the code.

All our benchmarks and valuation can be done using time, computation resources, memory and so on. We also need to have highest possible user satisfaction in the least amount of resources spent.
